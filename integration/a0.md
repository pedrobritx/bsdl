# A0 contextual routing and evidence contract (experimental)

**Status:** proposed integration slice; requires Polaris composition PR #9. This does not install an LLM service or autonomous execution harness.

## What exists

`automation/a0.py` extends the version-1, read-only `automation/constellation.py` planner. A real coding host must inspect the adopting product and supply explicit evidence-backed signals. A0 is deliberately **not a natural-language parser**; it never edits product files, executes tests, fetches the Internet or grants permission.

Routing chooses *applicable discipline coverage* separately from *agent multiplicity*. Axis covers implementation/architecture, Meridian interaction, Sentinel security. A host reporting available native subagents may use a coordinated or parallel recommendation; otherwise the default is one agent. Controlled human approvals are an additional independent overlay. A disabled required discipline remains `needs-coverage`, never silently passed.

## Usage in a local workspace

Have sibling checkouts named `polaris`, `axis`, `meridian`, `sentinel` (only selected enabled disciplines are required). Clone/checkout the adopting product separately. Adopt a project-specific `constellation.json` based on [project.example.json](project.example.json). Host inspects its actual source, approvals and user task, and writes a *task-scoped* intake file based on [a0-intake.example.json](a0-intake.example.json). Example values are **not** live evidence.

```sh
python3 polaris/automation/a0.py route \
  --config /path/to/product/constellation.json \
  --intake /path/to/product/a0-intake.json \
  --workspace /path/to/workspace \
  --product-root /path/to/product
```

The parser validates the supplied record, context paths, Git provenance, discipline opt-outs and available manifests; it returns a JSON plan with `routing.mode`, rationale and `preflight_status`. A `ready` preflight means **eligible to plan**, never performed work. Host capabilities are declarations rather than attested runtime features; set unsupported capabilities to false. Stop or secure an alternative review when `needs-coverage` appears.

After **authorized** host execution, the host may prepare a result based on [a0-result.example.json](a0-result.example.json) and validate its structure:

```sh
python3 polaris/automation/a0.py check-result --result /path/to/product/a0-result.json
```

This checks reported execution/verification/approval state, source-consistent check references, coverage gaps and high/critical findings. The checker does **not** independently execute, attest or verify that a test actually ran. Before human acceptance, review actual PR diff, CI/command logs, source revisions and documentation in the adopting project.

## Routing semantics

- Unified: default; one coding agent applies relevant discipline guidance.
- Coordinated: multiple selected concerns share interfaces, and the host explicitly reports supported specialist execution.
- Parallel: truly independent workstreams, actual subagents and isolated worktrees declared available, with no shared mutable interfaces.
- Controlled: `human_approval_required_for_consequential_action` is an overlay, not a substitute for the host's own enforced permissions. L0 permissions remain human-only regardless of flag value.

## Evidence invariants

- Execution, verification and approval are **separate** states.
- Failed, blocked, unverified or stale work cannot be labeled `verification=passed` by the schema validator.
- Every check reports a command, integer exit code, matching source revision, and evidence reference; no raw secrets or sensitive transcripts.
- Evidence references are *self-reported assertions*, not proof. Inspect actual logs, changed files, tests and independent observations.
- An outcome may be `schema-valid` while not safe to merge or release.
- A product with relevant disabled capability still needs alternate coverage, even if it can be built successfully.

## Current limitations and next work
